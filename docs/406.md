# arXiv HTTP 406 errors: what happens, and why

This page explains the HTTP 406 errors from the arXiv API. It is written for
a person who is new to this project. It uses short sentences and simple
words, in the style of [ASD-STE100 Simplified Technical
English](https://www.asd-ste100.org/).

## What is a 406 error?

An HTTP server sends status code 406 when it cannot give a response that
matches what the client asked for. The formal name is "Not Acceptable". See
the [MDN reference for HTTP 406](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/406)
for the full definition.

In most APIs, a 406 error means: the client sent an `Accept` header that the
server cannot satisfy. That is not what happens here. arXiv's export API
uses 406 for a different reason. See "Root cause" below.

## How this was detected

This project fetches arXiv papers with `ArxivClient`
([src/services/arxiv/client.py](../src/services/arxiv/client.py)). It calls
the arXiv export API at `https://export.arxiv.org/api/query`.

Two real incidents showed the 406 problem:

1. **Issue [#37](https://github.com/pkuppens/production-agentic-rag-course/issues/37).**
   The `arxiv_paper_ingestion` Airflow DAG failed with a 406 error during the
   `fetch_daily_papers` task.
2. **Issue [#39](https://github.com/pkuppens/production-agentic-rag-course/issues/39).**
   A manual DAG run got an HTTP 200 response. But the response body held one
   `<entry title="Error">` element, with the message `sortOrder must be in:
   ascending, descending`. The request already used `sortOrder=descending`,
   a valid value. So the error message was wrong. This was a second, related
   symptom, not a new problem.

## Root cause

Live testing found **two separate causes**. Both show up as a 406 error, but
they need different fixes.

### Cause 1: unescaped `[` and `]` characters in the URL

The client builds date-range queries with square brackets, for example
`submittedDate:[20240101 TO *]`. The old code kept these brackets unescaped
in the URL query string. Direct A/B testing (send the same query, once with
raw brackets and once percent-encoded) confirmed: arXiv's edge server
rejects a literal `[` or `]` in the URL with a 406 error. This is not
random. It happens every time.

**Fix:** percent-encode `[` and `]` in every query URL. Keep `:`, `+`, and
`*` unescaped, because arXiv's query syntax needs them as-is. See the `safe`
variable in
[`fetch_papers`](../src/services/arxiv/client.py) and
[`fetch_papers_with_query`](../src/services/arxiv/client.py).

### Cause 2: arXiv's own overload / load-shedding

Even a simple query, with no brackets and no date range, still failed with a
406 error, over and over. A live test sent the exact same `cat:cs.AI` query
8 times in a row. All 8 attempts got a 406 error, over about 70 seconds.
Then the very next attempt succeeded, with no code change at all.

This tells us the 406 error is not always about the query content. Under
load, arXiv's export API sheds requests with a bare 406 status. It does not
use the more common `429 Too Many Requests` status for this. The same kind
of overload can also show up as an HTTP 200 response, with the "Error" entry
described above under issue #39. Both are the same underlying behavior:
arXiv is busy, and it rejects the request for a short time.

**Fix:** treat a 406 (and a 429, and any 5xx status) as a signal to retry,
not as a permanent failure. Wait, then send the same request again. See
"What was fixed" below.

### Root cause assumptions that were rejected

The investigation also checked two other possible explanations, and ruled
them out:

- **"arXiv changed its API rules."** The error message said `sortOrder must
  be in: ascending, descending`. That looked like a validation error. The
  team checked arXiv's own
  [API user manual](https://info.arxiv.org/help/api/user-manual.html) for
  the current, allowed `sortOrder` values. The allowed values were
  unchanged, and `descending` was one of them. So this was not a real
  validation error. It was the overload behavior from Cause 2, shown through
  a fake error message.
- **"It only happens with date-range queries."** A query with no date range
  and no brackets still failed 8 times in a row. So the bracket problem
  (Cause 1) is not the only cause. This ruled out "brackets are the only
  problem" as a full explanation, and led to the discovery of Cause 2.

## What was investigated and implemented

All fixes live in `ArxivClient`
([src/services/arxiv/client.py](../src/services/arxiv/client.py)) and its
settings ([src/config.py](../src/config.py), `ArxivSettings`).

1. **Percent-encode `[` and `]`.** Closes Cause 1. See `fetch_papers`,
   `fetch_papers_with_query`, and `fetch_paper_by_id`.
2. **Classify errors by status code**
   (`_classify_http_status_error`):
   - `406` and `429` → `ArxivAPIRateLimitError`. Retryable.
   - `5xx` → `ArxivAPIServerError`. Retryable.
   - Any other `4xx` → `ArxivAPIClientError`. Not retryable. This is a real,
     permanent problem with the request (for example, a malformed query).
3. **Detect the embedded-error-in-200 shape** (`_extract_embedded_error`).
   If the XML body holds exactly one entry, titled `"Error"`, that links to
   the API user manual, the client treats it the same as a retryable server
   error, not as a parse failure.
4. **Retry with capped backoff** (`_get_with_retry`). On a retryable error,
   the client waits, then tries again. The wait time doubles each time
   (exponential backoff), up to a maximum of `metadata_max_retry_delay`
   (10 seconds by default). It retries up to `metadata_max_retries` times
   (8 by default). A fully exhausted retry run takes about 59 seconds before
   it gives up. This number comes from live testing, not a guess.
5. **Keep the documented rate limit.** Before every request, including
   retries, the client waits at least `rate_limit_delay` seconds (3 seconds
   by default) since the last request. This matches arXiv's own rate-limit
   rule (see "arXiv's suggested API" below).
6. **Split the Airflow ingestion task** (issue #37). The old
   `fetch_daily_papers` task did the arXiv fetch, PDF download, PDF parsing,
   and database save, all in one step. Now `fetch_metadata` (the arXiv API
   call) is a separate task from `process_and_store_papers` (download,
   parse, save). If `fetch_metadata` needs a retry, the pipeline does not
   redo PDF downloads or parsing that already finished.
7. **Skip the error in CI when it is not a real bug.** The automated test
   `test_arxiv_client_basic`
   ([tests/integration/test_services.py](../tests/integration/test_services.py))
   calls the real, live arXiv API. If arXiv is in one of its overload
   windows (Cause 2) during a CI run, the test now skips instead of failing
   the build. The client's own retry logic already tried its best; a skip
   says "arXiv was down, not our code," instead of blocking every other
   change in the same CI run.

### What is not fixed, because it cannot be

Cause 2 is arXiv's own server behavior, on arXiv's own infrastructure. This
project cannot make arXiv stop shedding load. The client can only wait and
retry, which is what it does. Expect occasional slow fetches (up to about a
minute) during arXiv overload windows. This is documented in the
`ArxivClient` class docstring.

## arXiv's suggested API: is it used?

arXiv publishes its own REST API for exactly this purpose. See the [arXiv
API overview](https://info.arxiv.org/help/api/index.html) and the [API user
manual](https://info.arxiv.org/help/api/user-manual.html).

**Yes, this project already uses it.** `ArxivClient` calls
`https://export.arxiv.org/api/query`
([`ArxivSettings.base_url`](../src/config.py)), which is the exact endpoint
the arXiv API overview page describes. The client also follows the two main
rules from the user manual:

- **Wait at least 3 seconds between requests.** Implemented as
  `rate_limit_delay` in `ArxivSettings`, enforced in `_get_with_retry`.
- **Use one connection at a time.** The client opens one `httpx.AsyncClient`
  request, waits for the response, then closes it, before it starts the
  next request.

What this project does **not** use is arXiv's official `arxiv` Python
package (a third-party wrapper around this same REST API, listed on
[PyPI](https://pypi.org/project/arxiv/)). `ArxivClient` builds and parses
the raw REST requests itself, with `httpx` and `xml.etree.ElementTree`. This
was a deliberate design choice already in place before this investigation,
not a gap found by it — the 406 errors happen at the level of the REST API
itself, so switching to the wrapper package would not change Cause 1 or
Cause 2. It is listed here for completeness, in case a future contributor
wonders why the wrapper package is not a dependency.
